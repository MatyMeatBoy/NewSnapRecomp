# NewSnapRecomp 0.7.1-tester

**Tester build, not stable.** Fixes on AMD RDNA 1/2 (RX 6900 XT tested) the photo, interface and
close failures that 0.7.0-tester only diagnosed. The 0.7.0 and earlier artifacts do not change.

## Changes since 0.7.0-tester

- **FOTO-01 fixed on AMD RDNA 1/2** (PR #15). The game encodes the photo thumbnail to BC1 by
  drawing through a block view of a 2D image. The AMD RDNA 1/2 driver writes outside those
  images' memory (the donor's issue #5, which there was avoided only for 3D BC). Now those draws
  go to an intermediate image that is copied to the texture.
  - Fixes the banded thumbnail, the strips on the frame, plate and portrait, and the
    `device fault … write invalid` closes.
  - New setting `AC_BLOCK_VIEWS` (`block_views` in the INI). It defaults to 0 on that driver and
    1 elsewhere, so nothing changes on NVIDIA.
- **CRISTAL-01 fixed on AMD:** the Crystabloom's crystal centre came out black on the RX 6900 XT,
  with a halo that the temporal antialiasing dragged along.
  - In the F12 dump, a single transparent draw left about 55,000 NaN pixels.
  - When creating each shader, the runtime now uses `NMin/NMax/NClamp` instead of
    `FMin/FMax/FClamp`. It is the Switch GPU's semantics: given a NaN they return the other
    operand, and `saturate` turns it into 0.
  - It also clamps the input of `sqrt`, `inversesqrt` and `log2` at 0.
  - Settings `AC_SPIRV_NMINMAX` and `AC_SPIRV_DOMAIN_CLAMP`: on on AMD, off elsewhere, so nothing
    changes on NVIDIA.
  - The same fix appeared independently in Lichii (#325, #432), Savage Wind (#153) and
    ocarina-recomp (#49). Guide for other recomps: `docs/bugs/amd-nan-shader-math.md`.
  - Checked on the RX 6900 XT: correct blue crystal and 0 passes with NaN in the new dump.
    `spirv-val` passes on the dumps' 89 distinct shaders.
- Documentation: cause, test and limits in `docs/bugs/amd-photo-gpu-fault.md`.
- **GYRO-01: turning the gyro on in the game's options no longer closes the game.**
  - Before, the SDK asked the `hid` service whether the sensor was at rest
    (`IsSixAxisSensorAtRest`, command 82) and the runtime ended with
    `FATAL: ipc: hid command 82 is not implemented`.
  - Now six-axis commands 68–83 are answered: the setters are accepted, the queries return the
    SDK's defaults, and «at rest» follows the controller's real motion.
  - Does not depend on the GPU.

## Checked

- **RX 6900 XT, driver 26.10.1** (runtime built with the 0.7.0 kit plus this change; the adapter
  produces byte for byte the same sources):
  - complete in-level thumbnail;
  - clean frame, plate and portrait;
  - photo selection screen and tutorial correct;
  - no `device fault` in two sessions, one of over 10 minutes at a steady 60 fps.
- Before the change, all four logs with a close on that machine ended in `write invalid`.
- Adapter tests and the PR's CI green.

## Not checked

- Not run on RTX with this binary (the default does not change there). Control:
  `AC_BLOCK_VIEWS=0` with the 540 s photo route.
- Long routes, the complete album and other levels on AMD.
- Pacing on AMD: the Windows driver does not offer `mailbox` and falls back to `fifo`. At 60 fps
  on a 100 Hz monitor there is cadence judder: 120 Hz or FreeSync is advisable.
  - The owner notices irregularity **when turning the camera quickly**. It fits that judder (each
    frame lasts 10 or 20 ms on screen, and it shows more in turns), but it is not measured.
  - That session's logs give 60.0 fps on average and a 1 % low of 49–58 fps, with isolated
    spikes of up to 54 ms in the fence/present wait.
  - Pending: repeat with the monitor at 120 Hz or with FreeSync on, and with a presentation
    `AC_TRACE`, to separate the monitor's cadence from real runtime spikes.
- More than 60 FPS, scales 125/150/200 % and complete routes.
